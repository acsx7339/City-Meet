# City-Meet：動態社群熱度地圖技術規格書 (MVP 精簡版)

本文件旨在將《City-Meet：動態社群熱度地圖專案企劃書》中的所有產品概念轉化為明確的系統設計規格藍圖。本規格書採用「簡化版三層式架構：前端 App/Web + 後端 API + PostgreSQL/PostGIS 資料庫」的實作策略，以最輕量化、高擴充性的方式快速投入市場，用以驗證「城市社交氣象台」的核心價值。

---

## 一、 整體系統架構 (Overall Architecture)

本專案在 MVP 階段採用精簡明瞭的三層式架構，旨在降低初期開發成本，並完美支撐高頻的地理空間運算與即時資訊推播需求。

```text
[ 使用者端 (手機 App / Web網頁) ] 
               │
               ▼ (透過標準 REST API 溝通)
    [ 後端 API 伺服器 (NestJS / Node.js) ]
               │
               ├─► [ 即時快取與媒體儲存 (Redis / S3) ]
               │
               └─► [ 核心關聯與地理空間資料庫 (PostgreSQL + PostGIS) ]
```

> **🎯 排除清單 (MVP 暫不需要)**
> 為避免架構過重影響產品落地速度，現階段明確排除：微服務架構 (Microservices)、Kafka 訊息佇列、大數據分析平台、即時 AI 推薦模型。商業端的高級城市活動數據儀表板後台在此階段僅於資料庫留存數據，暫不開發前端複雜圖表。

## 二、 前端核心視覺與 RWD 佈局規劃 (Frontend & RWD)

前端核心在於呈現現場大眾的「小心聲氣泡粒子」跟著「不同熱度分級的颱風氣旋」動態旋轉，並針對行動端與桌面端進行響應式佈局適配。

### 1. 建議技術選型

*   **Mobile App / Web 前端**：React Native (適配手機 App) 或 React / Next.js (Web 網頁)。
*   **地圖 SDK**：Mapbox SDK 或 MapLibre GL JS（支援自訂 WebGL 圖層，效能遠勝傳統 Google Maps Marker）。
*   **氣旋與小心聲動畫**：HTML5 Canvas API 或 WebGL 粒子系統（將心聲文字與貼圖轉換為精靈圖 Sprites 進行高效率渲染）。

### 2. 「小心聲粒子」氣旋旋轉演算法

每個活動座標在地圖上被視為一個「引力中心點 ($X_c, Y_c$)」。氣旋中的「小心聲（Mood Particles）」不使用傳統 DOM Element，而是依據極座標系 (Polar Coordinates) 動態計算旋轉軌跡：

$$X_{next} = X_c + r \cdot \cos(\theta + \omega \cdot t)$$
$$Y_{next} = Y_c + r \cdot \sin(\theta + \omega \cdot t)$$

*(其中 $r$ 為心聲粒子距中心半徑，$\omega$ 為角速度，$t$ 為時間幀)*

### 3. RWD 響應式佈局適配規則 (CSS Breakpoints)

*   📱 **行動端 (Viewport < 768px)** — 聚焦單手探索與即時決策：
    *   地圖層採用 100% 滿版呈現，方便使用者在大街上用單手手指縮放與盲操。
    *   點擊氣旋時，活動詳情、集合點標籤與即時抵達狀態一律從螢幕底部滑出「底部抽屜式組件 (Bottom Sheet)」。
    *   「今晚去哪裡」與 Filter 篩選器轉化為圓形浮動按鈕 (FAB Layout)，配置於單手大拇指操作熱區。
    *   粒子系統自動降低最大渲染數 40%，並微調旋轉角速度，以降低行動裝置耗電量。

*   💻 **桌面端 (Viewport >= 768px)** — 聚焦深度瀏覽與活動籌備：
    *   雙欄佈局 (Split-Screen Layout)：左側 35% 為固定高密度資訊看板（時間軸預報、個人化風向管理），右側 65% 為滿版動態地圖。
    *   支援滑鼠懸停 (Hover Event) 預覽，滑鼠移至氣旋上時，即跳出對話框即時預覽跟著風暴旋轉的「熱門小心聲粒子內容」。

## 三、 後端地理空間運算與核心模組 (Backend & GIS)

採用 PostgreSQL + PostGIS 作為核心，提供標準 REST API 接口，處理所有地理範圍查詢、群聚演算法與社交隱私保護。

### 1. 核心空間定位與社交邏輯 (Spatial Queries)

*   **「今晚去哪裡」決策篩選 (`ST_DWithin`)**：
    利用 SQL 的 `ST_DWithin` 地理半徑查詢，一秒過濾出使用者步行/車程 30 分鐘內的所有動態氣旋，並過濾出匹配分類標籤、且處於熱度增長階段（低壓形成至人氣風暴）的活動。

*   **「朋友雷達」隱私保護圍欄 (`ST_Contains`)**：
    系統以各氣旋之「集合點座標」為中心建立虛擬地理圍欄（Geofence）。若判定朋友的精準 GPS 落入該圍欄內：

    $$\text{ST\_Contains}(\text{活動圍欄}, \text{朋友精準位置}) = \text{True}$$
    
    API 絕對不回傳朋友的精準座標，僅回傳 `{"eventId": 123, "friendNicknames": ["小明"]}`。前端收到後僅將頭像/暱稱模糊呈現在該活動氣旋外圍，成功將陌生活動轉化為「半熟社交」場域，完美達到隱私保護。

*   **「氣旋共振」群聚演算法 (`ST_ClusterDBSCAN`)**：
    後端定時針對地圖區塊執行 `ST_ClusterDBSCAN` 空間群聚函數。當發現同一街區、同一時間內有數個屬性相近的小型 UGC 民間活動時，自動將其聚合為一個「大型區域父風暴（如：西門夜間創作氣旋）」，點擊後才展開多個子活動。

### 2. 雙軌活動來源同步 (Official Import Worker)

後端常駐一個背景排程服務（Cron Job），自動爬取政府公開資料 API（如各縣市政府展演、觀光局資料），將官方活動自動寫入資料庫並賦予初始熱度，確保前端一讀取即自動同步渲染為對應等級的颱風氣旋。

### 3. 「餘波系統」生命週期快取 (TTL System)

資料庫的活動與小心聲紀錄，透過後端設定 TTL (Time-To-Live) 快取控制或資料庫分區，確保活動結束後的 60 天（兩個月）內，使用者仍可在歷史圖層查閱該氣旋留下的「餘波殘留」（包含當時的心聲回顧與現場照片）。60 天後則自動消散歸檔，確保即時地圖的高速載入效能。

## 四、 氣旋熱度演算法與視覺映射 (Heat Score & Personalization)

MVP 階段不需要複雜的機器學習，採用直觀的 Rule-Based 加權公式計算熱度得分（Heat Score），並對應到地圖上的颱風大小。

### 1. 熱度計算公式

$$\text{Base Score} = (\text{報名人數} \times 3) + (\text{收藏人數} \times 1) + (\text{打卡人數} \times 5) + (\text{小心聲數量} \times 2) + \text{官方活動加權} - \text{時間衰退值}$$

### 2. 「同溫層風向」個人化加權機制

在 API 回傳前，系統會比對使用者的 `interest_tags`。若使用者具備該活動的標籤（例如使用者具備 `["美食"]` 標籤），則該活動的最終熱度得分為 $\text{Base Score} \times 1.5$ 倍。如此一來，美食氣旋在該使用者的畫面上會自動放大，形成專屬個人的「同溫層風向圖」。

### 3. 視覺大小與強度分級映射關係

後端計算出的最終 Heat Score 會直接映射至前端的氣旋半徑與流速參數：

*   🌪️ **Score 0 - 20**： 氣旋種子（地圖上的微弱小光點，活動剛建立）。
*   🌪️ **Score 21 - 60**： 熱帶低氣壓（零星小心聲氣泡，開始圍繞中心形成旋轉雲團）。
*   🌪️ **Score 61 - 150**： 輕度颱風（小型民間氣旋，心聲粒子開始穩定轉動）。
*   🌪️ **Score 151 - 500**： 中度颱風（中型氣旋，自動對接之官方活動基本規格，或是高人氣民間聚會）。
*   🌪️ **Score 500 以上**： 強烈颱風（巨型超級氣旋，如萬人跨年或大型耶誕城，暴風半徑與密集旋轉的心聲粒子串流達到頂峰）。

## 五、 資料庫架構規劃 (Database Schema Draft)

為滿足上述邏輯，系統核心資料表初步規劃如下（以關聯式設計為例）：

1.  **`users` (使用者表)**：
    `id` (PK), `nickname`, `interest_tags` (興趣標籤陣列), `trust_score` (安全氣象台：主辦人信任分數)。
2.  **`events` (活動氣旋表)**：
    `id` (PK), `title`, `source_type` (民間 UGC / 官方對接), `geom_location` (PostGIS 地理點座標物件), `assembly_point_desc` (精準集合點文字描述與標籤註記), `storm_level` (氣旋大小分級), `created_at`, `ended_at`。
3.  **`event_participants` (活動參與關聯表)**：
    `event_id` (FK), `user_id` (FK), `status` (即時抵達狀態，如：我出發了/我快到了/已抵達), `is_bookmark` (是否收藏)。
4.  **`event_mood_particles` (小心聲動態表)**：
    `id` (PK), `event_id` (FK), `user_id` (發送者), `content_text` (小心聲文字短句或對話), `sticker_id` (即時貼圖代碼), `created_at` (發送時間，用於粒子過期計算)。
5.  **`event_reports` (安全檢舉紀錄表)**：
    `id` (PK), `target_type` (檢舉活動/檢舉使用者), `target_id`, `reason_tag` (風險標籤), `reporter_id`, `created_at`。
6.  **`official_events` (官方資料對接暫存表)**：
    存放由 ETL 爬蟲定時抓取、尚未轉換為 `events` 格式的官方活動數據原始表。

## 六、 建議技術落地路線 (Deployment Stack)

為了最快打造出第一版 MVP 並驗證「城市社交氣象台」與「半熟社交」概念，強烈建議採用以下輕量化全棧堆疊：

*   🚀 **前端 (Frontend)**：React Native + Mapbox SDK (可同時打包成 iOS/Android 手機 App 並適配 Web 地圖流暢效果)。
*   🔐 **後端與認證 (Backend & Auth)**：直接串接 Supabase Edge Functions 與 Supabase Auth（大幅省去自行架設複雜後端應用伺服器與登入驗證的開發時間）。
*   🗄️ **資料庫 (Database)**：採用 Supabase 內建提供的雲端 PostgreSQL + PostGIS 資料庫，可以直接在資料庫後台利用標準 SQL 與空間函數進行所有的地理圍欄模糊化、今晚去哪裡半徑查詢與氣旋共振群聚運算。
*   ☁️ **媒體儲存 (Storage)**：使用 Supabase Storage 或 AWS S3，用以存放使用者在活動現場、暴風眼或結束後「餘波系統」中所掉落的現場照片與回顧紀錄。
